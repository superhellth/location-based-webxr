# 2026-07-31 — Component 7: 2D Map Overview (implementation plan)

## Context

Component 7 (TASK.md §2.3) is a toggleable 2D map showing the visitor's
real-time position and the tour's points of interest. The spec requires
investigating and building on **the same map component the recorder app
uses**, and — if it can't be reused directly — documenting why, while keeping
the interface compatible.

The contract is already agreed in `plans/Shared-Contract.md` (D5, D11, D17).
This plan implements it and does not rename the surface it defines. Resolved
in a design grilling with Maria on 2026-07-31.

Package: **`GpsPlusSlamJs_TourBuilder/`**. Core + view live under
`components/map/{core,view}/`, demo under `components/map/` (mirrors the
proximity/billboard layout).

---

## Investigation: which map component is "the" recorder map, and can we reuse it?

The recorder has **three** Leaflet-based UIs; only one is the live, toggleable,
real-time one the spec means:

| File                                                                                        | Purpose                                                                                                                                                         | Live/toggle? |
| ------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------ |
| `GpsPlusSlamJs_RecorderApp/src/ui/preview-map.ts`                                           | Static GPS-path preview on the replay setup screen                                                                                                              | No           |
| `GpsPlusSlamJs_RecorderApp/src/ui/summary-map.ts`                                           | Static post-hoc summary map after a recording ends                                                                                                              | No           |
| `GpsPlusSlamJs_AppFramework/src/visualization/leaflet-map-overlay.ts` (`LeafletMapOverlay`) | **The live map**, toggled during an active AR session (`main.ts`: `mapOverlay.toggle()` on a HUD button, `render(data)` driven by store subscribers every tick) | **Yes**      |

`LeafletMapOverlay` is confirmed (via `main.ts` + `main.map-toggle-wiring.test.ts`)
as the real, real-time, toggleable map — the correct "same component" target.

**Why it can't be reused directly (the required deviation + documentation):**
`LeafletMapOverlay`'s constructor takes `(scene: THREE.Scene, camera: THREE.Camera,
options)` and embeds its Leaflet map into the 3D scene via a `CSS3DObject`
positioned as a child of the camera/CameraFollower — a floating in-world panel,
not a flat screen overlay. That embedding exists so the map is visible inside an
immersive WebXR session (the same reason component 2's text labels need
HTML-in-3D, not a plain DOM overlay). But TASK.md is explicit for _this_
component: "a toggleable **HTML/2D map**" and its demo is "a **standalone map
page**" (matching components 5/6's plain-page demos, not components 1/2's
Three.js-scene demos, and unlike component 4's Three-type-only-import purity
rule the map should not need runtime Three.js at all). Wrapping the CSS3D class
would force a THREE.Scene/camera/CSS3DRenderer scaffold onto what the spec calls
a page, and would leak a Three.js dependency into a component whose own contract
line (D5) only ever mentions Leaflet.

**What IS reused (the real "build on it," at the correct seam):**

- `buildMapData()` (`GpsPlusSlamJs_AppFramework/src/visualization/map-data.ts`) —
  the exact same pure builder both the live CSS3D map and the flat 2D summary
  map already share. No new data-shaping logic.
- `drawMapData()` (`.../visualization/map-overlay-draw.ts`) — the actual
  Leaflet-layer-drawing routine both existing maps call for trajectory/user-dot
  rendering. Reused directly.
- `computeFusedPath` / `fusedGpsFromOdom` (`.../utils/fused-path.ts`) — pure
  odometry→GPS conversion, already used to build `MapData.fusedPath`. This is
  how the demo turns synthesized world-space waypoint anchors and the replayed
  user path into lat/lon for the map, with **zero new geo math** (TASK §2.5.1).
- `VIS_COLORS` + the named-marker visual conventions (size, halo, drop-shadow)
  from `LeafletMapOverlay.createNamedMarker`.
- **Public method shapes** (`setGpsPosition`, `render(data)`, `toggle()` /
  `show()` / `hide()` / `isVisible()`) are mirrored 1:1 so a future composition
  step (component 8) could wrap this flat component in a `CSS3DObject` exactly
  the way `LeafletMapOverlay` wraps its own Leaflet map, with **zero changes to
  this component's public interface** if immersive-mode embedding is ever
  needed. This is the "keep the interface compatible" half of the spec
  requirement.

## Decisions (resolved in the 2026-07-31 grilling)

| #   | Branch                                   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| --- | ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Reuse target                             | The pure/shared layer (`buildMapData`, `drawMapData`, `computeFusedPath`, `VIS_COLORS`), not the `LeafletMapOverlay` class itself. Documented deviation above.                                                                                                                                                                                                                                                                                                                                              |
| 2   | Module shape                             | Pure `core/map-marker-state.ts` (waypoint → marker view-model) + impure `view/tour-map.ts` (plain `L.map(container)`, no Three.js).                                                                                                                                                                                                                                                                                                                                                                         |
| 3   | Marker scheme                            | 3-state: `visited` (green, ✓) / `next` (highlighted, gold) / `unvisited` (neutral grey). `next` = `selectNextUnvisitedWaypoint` — a **visual hint only**, not a gate; proximity (component 4) activates any waypoint by distance regardless of order (order is not enforced).                                                                                                                                                                                                                               |
| 4   | "Visited" semantics                      | A waypoint is visited once its zone has reached `ACTIVE` **at least once** — not "currently active." Demo dispatches `markWaypointVisited(id)` on the zone transition **into** `ACTIVE` for the first time, driven by the real component-4 driver.                                                                                                                                                                                                                                                          |
| 5   | Position/marker units                    | Map works in lat/lon (Leaflet native), never world-space — this is the one place besides `tour.json` and the framework's anchoring step where geo coordinates legitimately appear (mirrors §2.5.1, and matches contract D5's "map converts to Leaflet `lng` on its side").                                                                                                                                                                                                                                  |
| 6   | Demo data source                         | Real Task 1 recording (`recordings/2026-06-22_16-06-59utc.zip`) via `replayRecording()` — not a synthetic path — because "visited" needs real component-4 zone transitions and the map needs real lat/lon, which only align from an actual replay (raw GPS + odometry + alignment matrix in the same tick).                                                                                                                                                                                                 |
| 7   | Waypoint anchor construction (demo only) | Synthesize world-space anchors from the replayed `odometryPositions` (same recipe as component 4's own e2e — self-consistent metric frame, D10 in the proximity plan), then convert those same points to lat/lon via `fusedGpsFromOdom(point, alignmentMatrix, zeroRef)` for map display and for the demo's `tour.json`-shaped fixture. No `createGpsAnchor` (that class is a continuous, frame-loop-driven live anchor for a rendered 3D object — the wrong tool for a one-shot static waypoint position). |
| 8   | Testing                                  | Pure core unit tests; view tests in jsdom against a real Leaflet map (same convention as `summary-map.test.ts`); a genuine replay e2e (position-follows-track assertion), per TASK's "component depends on movement → replay e2e" rule.                                                                                                                                                                                                                                                                     |
| 9   | Final, not prototype                     | Build the real, tested implementation directly — no throwaway prototype step (standing preference, see memory).                                                                                                                                                                                                                                                                                                                                                                                             |

## Architecture

### `core/map-marker-state.ts` — pure

```ts
import type { TourCoord, Waypoint } from "../../../store/types.js";

export type WaypointMarkerStatus = "visited" | "next" | "unvisited";

export interface WaypointMarkerViewModel {
  readonly id: string;
  readonly position: TourCoord;
  readonly status: WaypointMarkerStatus;
}

/** Pure. Same inputs -> same output. No Leaflet, no DOM. */
export function computeMarkerViewModels(
  waypoints: readonly Waypoint[],
  visitedIds: readonly string[],
  nextId: string | null,
): readonly WaypointMarkerViewModel[];
```

Algorithm: for each waypoint, `visited` if its id is in `visitedIds`; else
`next` if its id === `nextId`; else `unvisited`. Order preserved from input.

### `view/tour-map.ts` — the thin impure wrapper (plain Leaflet, no Three.js)

```ts
import type { MapData } from "gps-plus-slam-app-framework/visualization/map-data";
import type { WaypointMarkerViewModel } from "../core/map-marker-state.js";

export interface TourMapOptions {
  readonly containerSizePx?: { readonly width: number; readonly height: number };
  readonly tileServerUrl?: string; // default: same OSM URL as LeafletMapOverlay
  readonly onTileError?: (error: unknown) => void;
}

export interface TourMapInstance {
  setGpsPosition(lat: number, lon: number): void; // centers the map; same name/shape as LeafletMapOverlay
  render(data: MapData): void; // reuses buildMapData/drawMapData path
  setWaypoints(markers: readonly WaypointMarkerViewModel[]): void; // replaces marker layer wholesale
  toggle(): void;
  show(): void;
  hide(): void;
  isVisible(): boolean;
  getLeafletMap(): L.Map | null; // parity with LeafletMapOverlay, for tests/advanced use
  destroy(): void;
}

export function createTourMap(
  container: HTMLElement,
  options?: TourMapOptions,
): TourMapInstance | null; // null if container is null, mirrors preview-map/summary-map convention
```

Internals: a real `L.map(container)` (no off-screen container trick, no
CSS3DObject — the container IS the visible element), an OSM tile layer,
`drawMapData(leafletMap, data, { showUserPosition: true })` for the position
dot, and `L.marker` + `L.divIcon` for waypoint markers using the same
size/halo/drop-shadow visual convention as `LeafletMapOverlay.createNamedMarker`,
recolored per `WaypointMarkerStatus` (green/✓, gold/highlighted, grey).
`toggle()`/`show()`/`hide()` control the container's visibility (e.g.
`display: none`) rather than CSS3D attach/detach — the map itself is created
once and never torn down/recreated on toggle (simpler than `LeafletMapOverlay`,
which recreates cheaply because DOM insertion is the expensive part there; here
there's no insertion cost to avoid).

## Testing (two levels + jsdom integration)

### Unit (`core/map-marker-state.test.ts`) — pure, no Leaflet/DOM

- Empty waypoints → empty result.
- All three statuses assigned correctly given a mix of visited/next/neither.
- `nextId: null` (all visited) → no waypoint gets `next`.
- Input order preserved in output.

### View/integration (`view/tour-map.test.ts`) — jsdom + real Leaflet

Same convention as `summary-map.test.ts`/`preview-map.test.ts`:

- `createTourMap(null)` → `null`.
- `setGpsPosition` centers the Leaflet map at the given lat/lon.
- `setWaypoints` places one `L.marker` per view-model at the **expected
  lat/lng** (this is the "unit-test the geo→screen projection" line from
  TASK.md — verified via Leaflet's own marker `getLatLng()`/rendered position,
  not custom Mercator math, matching how the existing map tests already do
  this) and with the expected icon color per status.
- `render(data)` draws the user-position dot via `drawMapData`.
- `toggle()`/`show()`/`hide()`/`isVisible()` toggle container visibility.
- `destroy()` is idempotent.

### Replay e2e (`view/tour-map-replay.e2e.test.ts`) — real recording

- `replayRecording(recordings/2026-06-22_16-06-59utc.zip)` → `odometryPositions`,
  `alignmentMatrix`, `zeroRef` (same fixture and extraction recipe as
  `proximity-replay.e2e.test.ts`).
- Convert the full `odometryPositions` path to lat/lon via `computeFusedPath`
  (already-tested framework function — no new geo math).
- Feed each point through `createTourMap(...).setGpsPosition(lat, lon)` in
  order; assert the resulting Leaflet map center/position marker follows the
  track — i.e., each step's projected position matches the corresponding
  `computeFusedPath` entry, in order (the literal "assert the position marker
  follows the track" test line from TASK.md).

## Demo (`components/map/demo.ts` + `index.html`)

Final, integration-flavored — composes components 3 + 4 + 7 for real (no
reinvented zone logic, no fake "visited" check):

1. Load a small sample-tour fixture (`store/fixtures/sample-tour.ts` pattern):
   waypoints as `TourCoord` placed near points along the real recording's walk.
2. `replayRecording()` the fixture zip once at demo load: get `odometryPositions`
   (world-space, drives proximity), `alignmentMatrix` + `zeroRef` (drives
   lat/lon conversion for both the user path and the waypoint anchors, via
   `fusedGpsFromOdom` per waypoint and `computeFusedPath` for the path).
3. Synthesize waypoint world-space anchors from the same `odometryPositions`
   path (component-4-e2e recipe) and convert each to lat/lon for the tour
   fixture / map display.
4. Real `createViewingStore()` + real `createProximityDriver` (component 4):
   `setWaypointZone` on every transition; `markWaypointVisited(id)` dispatched
   on the **first** transition into `ACTIVE`.
5. A "Start replay" button steps through the recorded path: each tick feeds
   the world position to the proximity driver and the corresponding lat/lon to
   `tourMap.setGpsPosition` + `render()`; after each tick,
   `computeMarkerViewModels(selectOrderedWaypoints(state),
selectVisitedWaypointIds(state), selectNextUnvisitedWaypoint(state)?.id ??
null)` → `tourMap.setWaypoints(...)`.
6. A toggle button demonstrates `show()`/`hide()`.

No Three.js anywhere in the demo page.

## Resolved questions (2026-07-31 second grilling round)

1. **Marker recolor** — static color/size delta, no animation: `unvisited`
   neutral grey (default ~20px, the existing `REF_POINT_MARKER_SIZE_PX`
   convention); `next` gold/amber, slightly larger (24px) to stand out;
   `visited` green + ✓. No pulse — keeps the demo deterministic (screenshots,
   tests) and avoids unnecessary UI polish; a static delta is enough contrast
   on a small map.
2. **Resize handling** — expose a public `resize()` on `TourMapInstance` that
   calls `leafletMap.invalidateSize()`. Call it internally from the
   show/visibility-toggle path via `requestAnimationFrame` right after
   `display` flips back to visible — not a fixed timeout guess (unlike
   `preview-map.ts`'s 200ms). rAF guarantees the browser has applied the
   `display` change before Leaflet measures the container. Kept public too,
   for callers that resize the container themselves (responsive layouts).
3. **Wholesale marker redraw** — confirmed fine at realistic scale (a handful
   to a few dozen waypoints), matching the existing `drawTrajectory` /
   `addPriorMarkers` bulk-redraw precedent at similar scale. No diffing
   (YAGNI) — revisit only if profiling ever shows it matters.
